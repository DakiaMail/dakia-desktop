## Account replacement and shared-profile limits

Focused Reader, attachment, Desktop mutation and CLI checks now reject a durable pending account-namespace reset. A separate profile-operation coordinator serializes supported CLI provider work with Desktop account updates. Its real-process tests and independent review passed, including a real CLI command, cancellation and abrupt-child-exit release, and Store opening while the distinct operation lock remains held. These changes still need an unchanged-source cycle and new native observations. Desktop command placement was compiled and reviewed; dynamic Wry contention was not yet exercised.

`MS-I-015` remains narrower than a complete account-identity receipt contract. CLI selections carry a message ID and UIDVALIDITY, without a durable account-namespace generation. If a provider replacement and rebuild finish before an old selection is resolved, coincident account ID, mailbox, UID and UIDVALIDITY can identify a different provider message. A pending-reset check or operation lock cannot distinguish that old selection once replacement has completed. This remains an explicit account-isolation gap. Desktop state has the same unresolved boundary: the main account-updated handler does not immediately clear selection, detached Reader lacks account-update/rebuild invalidation, and persisted Compose seeds retain the account UUID without a namespace generation. Rebuild events eventually clear main-window state, which does not prove all detached or later actions safe. Local-only CLI search can also display retained catalogue metadata during reset; that is not replacement-provider fetch acceptance. `MS-H-015` does not establish arbitrary concurrent writes, old-binary coordination or direct database writer safety.
