# Dakia v0.4.4 usage analytics disclosure erratum

**Date:** 2026-09-15
**Released implementation commit:** [`8af5c397d81cc9aa60ddaca9b5eb15ecac9f6255`](https://github.com/DakiaMail/dakia-desktop/commit/8af5c397d81cc9aa60ddaca9b5eb15ecac9f6255)
**Applies to:** the [`v0.4.4`](https://github.com/DakiaMail/dakia-desktop/releases/tag/v0.4.4) release and its tagged [`docs/usage-analytics.md`](https://github.com/DakiaMail/dakia-desktop/blob/v0.4.4/docs/usage-analytics.md) disclosure
**Status:** erratum — documentation correction only

This erratum corrects the v0.4.4 usage-analytics disclosure document. It does
not change any released software. The v0.4.4 tag, its release assets, and the
released sender and collector implementations are not modified by this
erratum.

## What is wrong

The version of `docs/usage-analytics.md` tagged at v0.4.4 misstates two
payload fields and omits a third:

- It says Dakia reports its **major/minor version**. In fact the sender
  reports the **full application version** (for example, a three-part
  version string).
- It says Dakia reports the **operating-system family**. In fact the v0.4.4
  sender hardcodes `os` to `macos`; it is not detected from the running
  system at all. Missing this limitation overstates what the field conveys:
  because every report says `macos`, the field carries no information about
  the machine's actual operating system.
- It **omits `os_version`** entirely. The sender does detect and report the
  operating-system version, and the collector persists it as an aggregate
  dimension.

The underlying sender and collector behavior described below is unchanged:
it is documented now as it actually was in v0.4.4.

## What the optional first-party reporting actually does

**Off until opt-in and at most weekly.** Reporting is off until you choose
**Share anonymous statistics**. The sender never runs before that opt-in,
and once on it posts at most once per calendar week
(7 × 24 × 60 × 60 × 1000 ms between reports). Turning it off aborts any
in-flight report, cancels future reports immediately, and removes the local
rotating identifier and the local last-report marker.

**Payload fields.** The v0.4.4 report (schema 1) contains exactly:

- `schema` — the schema number (1);
- `month` — the reporting month (`YYYY-MM`);
- `rotating_install_token` — a random 128-bit hexadecimal identifier,
  described below;
- `app_version` — the **full** application version;
- `os` — hardcoded to `macos` (see the limitation below);
- `os_version` — the operating-system version detected at report time;
- `arch` — CPU architecture (`arm64`, `x64`, or `other`);
- `providers` — the distinct broad categories of enabled mail providers
  (`gmail`, `outlook`, `fastmail`, `icloud`, `yahoo`, or `other`).

The tag-time disclosure listed the app version and operating system
differently than this, as described under "What is wrong" above.

**`os=macos` is not truthful operating-system detection.** The v0.4.4
sender does not detect the operating system; it always writes `macos`
because Dakia currently ships as a macOS desktop app. This field therefore
does not detect, and should not be read as, the actual OS family of the
reporting installation.

**No identifiers of your mail.** The payload and collector exclude
mailbox, message, email address, and account identifiers, and there is no
permanent device identifier; the only identifier is the rotating token
described below.

## Collector, storage, retention

**Rotating token.** The `rotating_install_token` is a random value generated
per reporting month. Because it regenerates every calendar month, the token
included in one month's report cannot link that installation to a following
month. The collector hashes the token with a salt and uses the hash only to
deduplicate the current reporting period; no identity claim stronger than
that is made, and this document does not claim the reporting is anonymous
beyond the rotation of this token.

**Cloudflare's role.** `analytics.dakiamail.com` is a Dakia-owned Cloudflare
Worker backed by a D1 database. Cloudflare acts as the processors of the
HTTPS transport and the storage layer.

**Retention.**

- Token-hash deduplication rows (receipts) are deleted after **35 days**.
- Aggregate monthly counters are retained for **24 months**.

**Persisted aggregate dimensions.** The counters stored after deduplication
are keyed on `month`, full `app_version`, `os`, `os_version`, `arch`, and
the `providers` list (joined into a single category string). The rotating
token itself, and the receipt hash derived from it, are not part of the
persisted aggregate dimensions.
